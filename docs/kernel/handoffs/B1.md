## 持久行为和集成要点

- Task/Run 存于 B1 独立迁移命名空间 `durable_tasks`，Bot 外键有效。提交的规范化原始 payload 用于 `(bot_id, idempotency_key)` 幂等冲突检测；默认预算变更不会改变原请求重试所得任务。事务领取预分配独立 Run/Session ID；每 Task 只有一个活动 Run，任务修订号通过 CAS 更新。
- Task.budget 是原始总上限，Task.cumulative_metrics 是已用额度。B3 从两者计算本次剩余额度；每个 Run checkpoint 从零累计，按与已记快照之差计费，重复快照不涨 revision。finish 原子计最后增量；reconcile 使用已记快照、日志尝试计数和最终结果的逐字段最大值作为恢复下界，绝不因缺日志退款。模型/工具尝试与 parent 已包含的 child 指标不能再次重复计入。等待期间没有活动 Run，也没有额外时间计费。
- queued 任务若模型/工具/时间任一预算耗尽，claim 将其 failed 并保留原因，不创建新 Run；执行中额度约束仍由 B3 真实 runner 负责。finish 正常 completed→succeeded、failed→failed、canceled→cancelled；paused 仅在合法交互参数下进入等待，否则 failed 并保留 reason。已有取消请求优先于普通结果/等待状态；未知副作用优先于所有这些终态映射。
- approval 等待需要精确 OperationIntent 和 interaction；question 需要 interaction。wake 保留 intent/interaction，只有当前等待关联吻合才入队；重复和过期 wake 不重复运行。B3 必须轮询 B2.ready() 并调用 wake，B1 不访问 B2 表。
- queued/waiting 可直接取消；running 只记 cancel_requested，worker 轮询调用 runner.cancel，并在 runner 实际结束后结算。needs_reconciliation 上取消仅记请求，不抹去未知副作用，仍须 resolve。resolve 限定 retry/fail/cancel，必须非空人工说明，独立 SQL 审计表保留 action/note/run ID；取消请求不能被 retry 绕过。
- claim 后无任何运行证据可结束占位 Run 并重新入队。worker 在调用 runner.run 前标记 SQL started，因此这之后、JSONL 写 run.started 之前的小窗口按“已 started SQL 缺日志”保守进入 needs_reconciliation。已结束日志可幂等结算；工具副作用未知不自动重放。对相同 RunEvidence 重复调用在之后新 Run 或人工 resolve 后也不会复写当前状态。
- **B3 正常返回路径必须设置 unknown_side_effect。** 该字段不能靠 reason 字符串猜测。worker 收到 True 时以原领取 Run/Session ID 构造 RunEvidence，带完整结果、metrics 和等待关联，调用 reconcile 而非 finish；TaskStore 验证结果关联并进入 needs_reconciliation。重启路径同样必须从真实 journal 得到 RunEvidence.unknown_side_effect。结果 persistence_failed 则直接传播 PersistenceError，保留活动 Run 供恢复，不声明成功。
- worker 构造时取得数据库目录中的 worker.lock 非阻塞 OS flock，保持到 close；每次 tick 首先恢复遗留 RUNNING。恢复损坏或错误关联直接停止；tick/recover 串行。关闭、serve stop、取消调度协程都等待 runner 实际停止再关闭 runner/释放锁；锁文件不删除，进程退出由 OS 释放。runner/checkpoint/polling/finish/close 故障均传播，失败执行不会伪造终态。
