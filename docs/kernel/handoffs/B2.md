# B2：持久审批与提问交接

2026-11-02。R1 PASS 后实现完成；只新增本节点的三个文件，没有修改共享契约、BotStore、TaskStore 或运行时。B2 模块自检通过，完整集成与 R2 验收仍由后续节点执行。

## 变更与接口

- `src/hiro_agent/interactions.py`：实现冻结 `InteractionService` 的全部方法，生产类为 `InteractionStore(database, bots)`。
- `tests/test_interactions.py`：49 项真实 SQLite 测试，覆盖独立连接竞争创建/答复/消费、数据库重开、权限和消费审计边界。
- `docs/kernel/handoffs/B2.md`：本交接。

迁移使用独立 `interactions` 命名空间和表，只保存 Task/Bot 文本 ID，不引用或查询 Task 表。创建时通过 BotStore 检查 Bot 存在，并重新验证可变请求 DTO，保证操作与请求 Task/Bot 一致；真实 Task 归属仍须由 B3 在入口校验。`(task_id, idempotency_key)` 对完整规范化请求去重，冲突抛出 `ConfigurationError`。

答复同样重新验证 DTO：审批必须是严格 bool，问题必须有非空白文本。合法审批附带的说明文本会保留；问题文本原样保存。相同完整答复在 answered/consumed 状态均幂等返回，冲突或已取消交互拒绝答复。缺失记录、所属 Bot 不符及非法请求/答复使用 `ConfigurationError`；SQLite 或保存内容损坏使用 `PersistenceError`，不会降级为普通授权拒绝。

`ready()` 每次读取所有 answered 记录，不修改状态，因此重开数据库后仍能提供未完成的唤醒。授权/答案成功消费后持久保存消费 Run ID 和时间，后续调用一律不再返回授权或答案；取消仅更新 pending/answered，保留答复和已消费记录。

授权消费在 `BEGIN IMMEDIATE` 内核对 Task、Bot、工具、规范化参数、权限版本/摘要以及 `approved=True`，再调用 BotStore 的公开 authority API 检查当前版本、摘要、白名单和可写权限。两个 store 必须指向同一数据库；事务的写锁阻止 BotStore.save 与检查/消费交错，无需复制 Bot SQL 布局。原始 Run/call/intent ID 用于追溯，不加入 binding，新 Run 可携相同绑定消费。空白消费 Run ID、错配、尚未答复、拒绝、取消、重复消费均不发放权限。

## B3 接入注意

1. 每次启动及 polling 调用 `ready()`，逐项使用 `wake(task_id, interaction_id)`；B2 不直接写 Task SQL。
2. `approved=False` 也保留在 ready 清单。`consume_authorization` 返回 False 并不消费它；B3 完成拒绝处理、取消或发现 Task 已终止后，应调用 `cancel_for_task(task_id)` 清理未消费的唤醒项，历史答复仍保留。
3. 消费失败不能转用普通审批 callback。成功消费后若尚未启动工具便崩溃，数据库不会返还授权；是否请求新的交互由 B3 根据执行证据决定。
4. B2 不验证消费 Run/Task/Session 的真实表关联；B3 负责实际 Task 所属、当前等待交互和新 Run 的匹配，以及执行前的当前权限复查。
